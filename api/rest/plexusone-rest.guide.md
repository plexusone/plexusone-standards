# PlexusOne REST API Guidelines

House REST API style guide for PlexusOne products (DashForge, ActionForge, AgentForge, SystemForge, OmniNotebook) and the crossforge interop contract. Derived from the api-style-spec default profile with PlexusOne-specific rules for PRN resource references, authorization scopes, run resources, and streaming. Self-contained rather than relying on `extends` resolution (the api-style-spec loader treats `extends` as schema-only metadata, not inherited rules) — restated rules cite their source as `default PO-xxx`.

## Design Principles

### Go Types Are the Source of Truth

API schemas are generated from Go types (Huma v2, invopop/jsonschema), never hand-authored. The OpenAPI 3.1 document is a build artifact committed alongside the code that produced it.

### One Suite, One Surface

All Forge products expose the same API conventions so a client, SDK, or agent that learns one Forge API can use them all. Consistency across products outranks local optimization within one product.

### Interop-Native Resources

Every addressable resource has a PRN (PlexusOne Resource Name, a resourceref-validated prn:// URI) and every API is a potential crossforge invocation target. Cross-product references always use PRNs, never bare IDs or ad hoc URLs.

### Agent-Consumable by Construction

APIs are designed to be projected into agent tools mechanically (omniskill's OpenAPI loader, MCP). Every operation has a precise operationId, summary, description, and typed request/response schemas.

### Library First, Thin HTTP

HTTP handlers are thin adapters over importable service-layer packages. Business logic is testable without the server.

### Additive Evolution

Within a major version, changes are additive only. Breaking changes require a new version segment and a deprecation lifecycle for the old one.

## General Guidelines

Fundamental requirements for all PlexusOne APIs

### PX-001: Provide OpenAPI 3.1 specification generated from Go types

**Severity:** error

All product APIs MUST publish an OpenAPI 3.1 specification. The specification MUST be generated from Go types (Huma v2 typed handlers or invopop/jsonschema), never hand-authored, and committed alongside the code that produces it.

**Rationale:** OpenAPI 3.1 aligns with JSON Schema draft 2020-12 and enables SDK generation, agent-tool projection (omniskill's OpenAPI loader, MCP), and contract diffing in CI. Generating from Go types keeps one source of truth per the PlexusOne Go-first convention.

**Examples:**

Good:

- `openapi: 3.1.0 (generated by Huma from typed handlers)`

Bad:

- `swagger: 2.0`
- `Hand-maintained openapi.yaml drifting from handlers`

**References:**

- [default PO-001, PlexusOne org conventions]()

## Naming Conventions

Property, resource, and identifier naming

### PX-002: Use camelCase for property names

**Severity:** error

All JSON property names in API and document surfaces MUST use camelCase (e.g., ruleId, createdAt, conformanceLevels). Exceptions: external specs always win (OpenAI-compatible endpoints use snake_case per the omniagent-rest profile; OTel/OTLP follow semconv), and custom telemetry event schemas use snake_case per the PlexusOne JSON & Naming Conventions.

**Rationale:** camelCase matches the PlexusOne convention for API/document formats and generates idiomatic clients. Deviating surfaces are governed by their own profiles rather than ad hoc exceptions.

**Examples:**

Good:

- `ruleId`
- `createdAt`
- `orgId`
- `conformanceLevels`

Bad:

- `rule_id (snake_case on an API surface)`
- `RuleId (PascalCase)`
- `rule-id (kebab-case)`

**References:**

- [default PO-002, plexusone org CLAUDE.md JSON & Naming Conventions]()

## URL Design

Resource-oriented URL patterns

### PX-003: Use kebab-case URL paths under /api/v{N}/

**Severity:** error

Product API paths MUST be kebab-case and live under a versioned prefix /api/v1/ (DashForge convention). Utility endpoints (/health, /livez, /readyz, /docs, /openapi.*, /.well-known/*) are exempt from the version prefix. A genuinely OpenAI-compatible surface (/v1/chat/completions) is governed by the separate omniagent-rest profile, not by an exemption in this rule's pattern — a repo running one adds an explicit path-scoped exception rather than this rule silently accepting any bare /v{N}/... path.

**Rationale:** A uniform /api/v{N} prefix across the Forge suite makes versioning explicit and lets the multiapp host route and gate consistently. Kebab-case avoids case-sensitivity issues and matches the org URL convention.

**Examples:**

Good:

- `/api/v1/notebooks`
- `/api/v1/style-profiles/{id}`
- `/health`
- `/docs`

Bad:

- `/api/v1/styleProfiles`
- `/notebooks (unversioned product endpoint)`
- `/api/v1/Notebook_Runs`
- `/v1/users (missing the api/ prefix)`

**References:**

- [default PO-003/PO-005, DashForge /api/v1 convention]()

---

### PX-004: Use plural nouns for collection resources

**Severity:** error

Collection resources MUST be plural nouns: /notebooks not /notebook, /workflows not /workflow.

**Rationale:** Plural collections are the suite-wide convention; GET /notebooks returns many, GET /notebooks/{id} returns one.

**Examples:**

Good:

- `/api/v1/notebooks`
- `/api/v1/workflows/{id}/runs`

Bad:

- `/api/v1/notebook`
- `/api/v1/run-list`

**References:**

- [default PO-004]()

## HTTP Methods

HTTP verb usage and semantics

### PX-005: Use standard HTTP methods correctly

**Severity:** error

GET (read, no side effects), POST (create or invoke), PUT (full replace), PATCH (partial update), DELETE (remove). Verbs never appear in paths except for invocation actions modeled as sub-resources (e.g., POST /api/v1/notebooks/{id}/runs to start a run).

**Rationale:** Correct method semantics enable caching and idempotency guarantees. Modeling invocation as run-resource creation (rather than /execute verbs) keeps long-running operations resource-oriented.

**Examples:**

Good:

- `GET /api/v1/notebooks/{id}`
- `POST /api/v1/notebooks/{id}/runs`
- `DELETE /api/v1/notebooks/{id}`

Bad:

- `POST /api/v1/notebooks/{id}/delete`
- `GET /api/v1/runNotebook?id=x`

**References:**

- [default PO-008]()

## HTTP Status Codes

Status code usage

### PX-006: Return 201 with Location for creation, 204 for deletion

**Severity:** warn

POST creating a resource SHOULD return 201 Created with a Location header. Successful DELETE SHOULD return 204 No Content. POST starting an asynchronous run SHOULD return 202 Accepted with the run resource in the body (see PX-012).

**Rationale:** Explicit creation and deletion semantics; 202 distinguishes accepted-but-running work from completed creation.

**Examples:**

Good:

- `HTTP/1.1 201 Created\nLocation: /api/v1/notebooks/nb_abc123`
- `HTTP/1.1 202 Accepted (run started)`
- `HTTP/1.1 204 No Content (deleted)`

Bad:

- `HTTP/1.1 200 OK for creation with no Location`

**References:**

- [default PO-010/PO-011]()

## Request & Response

JSON payload structure and conventions

### PX-009: Use prefixed string identifiers and ISO 8601 UTC timestamps

**Severity:** error

Resource identifiers MUST be strings with a resource-type prefix (nb_, run_, wf_, agt_). Date-time values MUST be ISO 8601 in UTC (2026-08-27T14:30:00Z); dates as YYYY-MM-DD.

**Rationale:** Prefixed string IDs are self-describing in logs and PRNs, support UUID/ULID backends, and avoid integer overflow. ISO 8601 UTC is unambiguous and sortable.

**Examples:**

Good:

- `nb_01J8ZK3V9XQ4`
- `run_abc123`
- `2026-08-27T14:30:00Z`

Bad:

- `12345 (integer id)`
- `01/15/2026`
- `1705329000 (epoch in JSON)`

**References:**

- [default PO-020/PO-021]()

## Error Handling

RFC 9457 error responses

### PX-007: Use RFC 9457 Problem Details for errors

**Severity:** error

All error responses MUST use RFC 9457 Problem Details (application/problem+json) with type, title, status, and detail. Product-specific extension members use camelCase.

**Rationale:** One error shape across the Forge suite means one error handler in every client, SDK, and agent tool wrapper.

**Examples:**

Good:

- `{"type": "https://plexusone.dev/problems/validation", "title": "Validation failed", "status": 400, "detail": "cellId is required", "invalidParams": [...]}`

Bad:

- `{"error": "bad request"}`
- `{"code": 400, "message": "oops"}`

**References:**

- [default PO-006]()

## Pagination

Cursor-based pagination

### PX-008: Use cursor-based pagination

**Severity:** warn

Collection endpoints SHOULD use cursor-based pagination: request parameters cursor and limit; response envelope with items and nextCursor (absent or null when exhausted).

**Rationale:** Cursors remain correct under concurrent writes and scale past offset limits; a single envelope shape keeps SDK generation uniform.

**Examples:**

Good:

- `GET /api/v1/notebooks?cursor=eyJpZCI6...&limit=50 -> {"items": [...], "nextCursor": "..."}`

Bad:

- `GET /api/v1/notebooks?page=3&pageSize=50`
- `Unbounded collection responses`

**References:**

- [default PO-007]()

## Versioning & Compatibility

API versioning, deprecation, and breaking-change policy

### PX-015: Additive-only changes within a version; detect breaking changes in CI

**Severity:** error

Within /api/v1, changes MUST be additive: new endpoints, new optional fields, new enum values only where documented as open. Removing/renaming fields, tightening types, or changing semantics requires /api/v2. CI MUST run api-style diff (breaking-change detection) against the previous released spec. Deprecations use the Deprecation and Sunset headers plus deprecated: true in the spec.

**Rationale:** Forge APIs are the suite's public contract (and eventually the cloud service's front door); additive evolution is what lets crossforge callers, SDKs, and agent tools pin a version and trust it.

**Examples:**

Good:

- `Adding optional field labels to Notebook schema in v1`
- `api-style diff old.yaml new.yaml in the CI workflow`

Bad:

- `Renaming createdAt to created in v1`
- `Making an optional request field required without a version bump`

**References:**

- [default compatibility/deprecation categories, crossforge design]()

## Security & Authorization

SystemForge-based authentication and scope conventions

### PX-010: Authenticate with SystemForge: Bearer tokens for APIs, BFF sessions for first-party web

**Severity:** error

APIs MUST authenticate via SystemForge: OAuth 2.0 / JWT Bearer tokens (including RFC 7523 service accounts and API keys) for programmatic access. First-party web frontends use SystemForge BFF server-side sessions (HTTP-only cookies) and MUST NOT expose tokens to the browser. securitySchemes MUST be of type http (bearer), oauth2, or openIdConnect.

**Rationale:** One identity platform across the suite: SystemForge owns authn (Fosite OAuth2/OIDC), so no Forge rolls its own token format, and agents/services use workload identity rather than user credentials.

**Examples:**

Good:

- `Authorization: Bearer <systemforge-issued JWT>`
- `securitySchemes: {bearerAuth: {type: http, scheme: bearer}}`

Bad:

- `X-API-Key: secret123 as the only scheme`
- `JWTs stored in browser localStorage`

**References:**

- [SystemForge session/bff and session/middleware; AgentForge BFF precedent]()

---

### PX-011: Name OAuth scopes as {app}:{resource}:{verb}

**Severity:** error

OAuth scopes MUST follow the suite convention {app}:{resource}:{verb}, e.g. dashforge:notebook:run, actionforge:workflow:trigger. Authorization uses the two-gate model: the principal's role permission AND the token scope must both allow the action.

**Rationale:** App-namespaced scopes map one-to-one onto SystemForge authz resource types ({app}.{resource}) and PRN app/resourceType segments, so a scope, a resource type, and a PRN all describe the same thing.

**Examples:**

Good:

- `dashforge:notebook:run`
- `actionforge:workflow:trigger`
- `agentforge:agent:read`

Bad:

- `notebooks.run (no app namespace)`
- `admin (unscoped)`
- `dashforge_notebook_run`

**References:**

- [ActionForge authz package, SystemForge INIT-SYSTEMFORGE-001 scope convention]()

---

### PX-016: Scope tenancy from the authenticated principal, not the URL

**Severity:** warn

Organization/tenant context SHOULD derive from the authenticated SystemForge principal (membership + org), not from client-supplied URL segments or headers. Cross-org access is only expressible via PRNs (which embed the org) and must pass authorization for both principal and target org.

**Rationale:** Deriving tenancy from the session/token prevents confused-deputy bugs and matches the SystemForge Organization + RLS model; PRNs make deliberate cross-org references explicit and auditable.

**Examples:**

Good:

- `GET /api/v1/notebooks (org from session)`
- `Explicit cross-org read via prn://plexusone/dashforge/org_other/notebook/nb_1`

Bad:

- `GET /api/v1/orgs/{orgId}/notebooks trusting orgId from the path without principal check`
- `X-Org-ID header as the tenancy source`

**References:**

- [SystemForge Organization/RLS model]()

## Crossforge Interop

PRN references, invocation, and run resources

### PX-013: Reference cross-product resources by PRN

**Severity:** error

Any field referencing a resource owned by another Forge product MUST carry a PRN — a prn:// URI validated against the resourceref/scheme.Profile format (prn://{authority}/{app}/{org}/{resourceType}/{id}[@{version|alias}] for tenant-scoped resources, prn://{authority}/{resourceType}/{path...} for ecosystem artifacts) — not a bare id or ad hoc URL. Fields holding PRNs are named with a Prn suffix (workflowPrn, notebookPrn). Production references to executable resources SHOULD pin a version or alias (e.g. @prod).

**Rationale:** PRNs make cross-product references resolvable, authorizable (they map to SystemForge resource types), and version-safe via the crossforge registry — bare IDs are ambiguous the moment two products both have a 'run 123'. Fields that don't need a PlexusOne-owned scheme should still be typed resourceref.ResourceRef (any URI, per the owner-canonical-passthrough rule) rather than a bare string.

**Examples:**

Good:

- `"workflowPrn": "prn://plexusone/actionforge/org_1/workflow/nightly-etl@prod"`
- `"notebookPrn": "prn://plexusone/dashforge/org_1/notebook/churn-model@14"`

Bad:

- `"workflowId": "123" (cross-product bare id)`
- `"notebook": "https://dash.example.com/notebooks/123"`

**References:**

- [resourceref (github.com/plexusone/resourceref) and crossforge interop design]()

## Streaming & Long-Running Operations

SSE, WebSocket, and async run patterns

### PX-012: Model long-running work as run resources with PRNs and normalized status

**Severity:** error

Long-running operations MUST be modeled as run resources: POST creates the run (202 Accepted), the response body carries the run's id, prn, and status, and GET on the run resource polls it. Run status MUST use the normalized crossforge vocabulary (PENDING, RUNNING, SUCCEEDED, FAILED, CANCELLED, TIMED_OUT) — never product-local status enums.

**Rationale:** Every Forge starts runs (workflow runs, notebook runs, agent runs). One run shape and one status vocabulary give the suite a single lineage, polling, and UI model, and make any run a crossforge invocation result.

**Examples:**

Good:

- `POST /api/v1/notebooks/{id}/runs -> 202 {"id": "run_abc", "prn": "prn://plexusone/dashforge/org_1/notebook-run/run_abc", "status": "RUNNING"}`
- `GET /api/v1/notebooks/{id}/runs/{runId} -> {"status": "SUCCEEDED", ...}`

Bad:

- `POST /api/v1/notebooks/{id}/execute blocking for minutes`
- `"status": "done" (product-local vocabulary)`

**References:**

- [crossforge run.RunStatus vocabulary]()

---

### PX-014: Stream with SSE for server push; WebSocket only for bidirectional sessions

**Severity:** warn

Server-push streaming (run status, log tails, progress events) SHOULD use Server-Sent Events (text/event-stream). WebSocket is reserved for genuinely bidirectional sessions (e.g. notebook kernel channels). Streamed events use the shared envelope with camelCase fields and carry the subject's PRN. Long-polling MUST NOT be introduced.

**Rationale:** SSE works through proxies and browsers with no client library, matches the ActionForge logstream precedent, and one event envelope keeps run-watching identical across Forges.

**Examples:**

Good:

- `GET /api/v1/runs/{id}/events (text/event-stream)`
- `WebSocket for kernel stdin/stdout sessions`

Bad:

- `WebSocket for one-way log tailing`
- `Client polling every 500ms as the documented pattern`

**References:**

- [ActionForge logstream/live SSE precedent]()

## Documentation

OpenAPI specification requirements

### PX-017: Use verbResource operationIds and document every operation

**Severity:** error

Every operation MUST have an operationId in verbResource camelCase form (listNotebooks, createNotebookRun, getWorkflow), a one-line summary, and a description. Every schema in components/schemas MUST have a description.

**Rationale:** operationIds become SDK method names and agent tool names via the omniskill OpenAPI loader — sloppy operationIds become sloppy tools. Summaries/descriptions are the tool docs agents read.

**Examples:**

Good:

- `listNotebooks`
- `createNotebookRun`
- `getWorkflowRun`

Bad:

- `notebook_list`
- `NotebooksGET`
- `doRun`

**References:**

- [default PO-040/PO-028, agent-consumable principle]()
